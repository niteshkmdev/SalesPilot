# docs/06-database-schema.md

# Database Design

Project: SalesPilot

Version: 1.0

Status: Final

---

# Purpose

This document defines the complete database architecture for SalesPilot.

It is the source of truth for:

- Prisma Schema
- MongoDB Collections
- Relationships
- Indexes
- Constraints
- Soft Deletes
- Future Scalability

Every model exists for a reason.

Avoid creating models "just in case."

---

# Design Principles

The database should optimize for:

✓ Readability

✓ Maintainability

✓ Query Performance

✓ Multi-tenancy

✓ Future SaaS Expansion

✓ Soft Deletes

✓ Auditability

# General Rules

Every collection should use

```ts
id
```

generated by Prisma.

Never manually generate IDs.

---

# Timestamps

Every mutable entity contains

```ts
createdAt

updatedAt
```

---

# Soft Delete

Every business entity contains

```ts
deletedAt

deletedBy
```

except immutable entities like Activity.

Soft deleted records must never appear in normal queries.

---

# Multi-Tenant Strategy

Every business entity belongs to an Organization.

This prevents future migration pain.

Example

```
Lead

↓

Organization

↓

OrganizationMember
```

Never store tenant information on User.

Phone

# Lead Merge

A merge

does NOT

update existing lead.

Instead

```
Lead A

Lead B

↓

Merge Wizard

↓

Lead C

↓

Soft Delete A

↓

Soft Delete B
```

Activity records preserve lineage.

Future

```

```

may be introduced if needed.

# Cascade Rules

Organization Deleted

↓

Soft Delete Members

↓

Soft Delete Leads

↓

Soft Delete Forms

↓

Soft Delete Branding

User Deleted

↓

Never

Users remain global accounts.

Membership removed instead.

Lead Deleted

↓

Soft Delete Attachments

↓

Activities remain.

Notifications remain.

# Index Strategy

Primary indexes

Email

Status

Member

Manager

CreatedAt

Name

Company

Email

Phone

Custom Fields

Avoid unnecessary indexes.

# Soft Delete Rules

Queries

Always exclude

```
deletedAt != null
```

Restoration is out of scope.

Hard deletes should never occur through the application.

# Final Database Goals

The schema should satisfy:

✓ Clean relationships

✓ Minimal duplication

✓ Strong multi-tenant support

✓ Efficient querying

✓ Predictable indexes

✓ Easy maintenance

✓ Future SaaS scalability

The database should be understandable without reading application code.
